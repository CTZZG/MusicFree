## 做了什么，为什么

上一轮证明原生引擎进度与通知投影有区别，但独立调用 MpvPlayerModule，没有经过真实 React/JS、插件、
切歌事务和音质提交流程。Android 14 的完整端到端主要看媒体会话，在 Android 16 Live Update 每秒刷新
会话的情况下，估算位置可能掩盖引擎停住。这次把两种验证连接起来。

没有修改产品实现。新增 Android 仪器测试启动真实 MainActivity/ReactHost，使用产品安装和搜索深链、
无障碍树上的实际控件、MediaSession transportControls，驱动真实 TrackPlayer 和测试插件。
测试反射读取这个 ReactHost 现有模块持有的 libmpv 句柄，检查 identity；没有备用引擎，没有缺读数时的估算回退。
只有故障对照会直接干预引擎。界面点击先用 ACTION_CLICK，必要时使用选中控件的实际 bounds，不用屏幕固定百分比。

首次启动前写入当前 App.config 的现有存储格式，让真实 JS 配置 Live Update、默认 192K、搜索替换队列，
关闭自动换源。每个样本检查真实通知模板是 ProgressStyle。这不等于验收用户点击 Live Update 设置开关。
注意：AppConfig.setConfig 将配置值 JSON.stringify 后存为字符串，布尔配置也必须是 `t=s, v="true"`，
字符串配置的 v 中必须保留 JSON 引号。`$schema` 和迁移标记是存储层专用字段，按其原始字符串格式写入。
API36 回归 #30 已经通过真实 JS 点播 B，但发现通知为 MediaStyle；原因是测试最初把配置按存储原始类型写入，
AppConfig 未读到开关。后续修正配置编码，不把这个运行算作 Live Update 场景通过。

## 正常场景

| 阶段 | 要证明的行为 |
| --- | --- |
| baseline | 真实 JS 点播 B，JNI 与会话都持续前进 |
| slow-skip-wait / slow-skip-playing | C 取源十二秒期间旧曲暂停，随后确实加载并播放 C |
| timeout-wait / timeout-rollback | Hang 插件不回应，旧曲暂停等待，在一次期限内回到 C 并保持非零进度 |
| quality-interrupted-old / quality-interrupted-new | C 慢速换到 320K，外部应用持有临时焦点时，旧源和新源的引擎均保持暂停 |
| quality-focus-resumed | 辅助应用明确释放焦点后，新源实际恢复并前进 |
| user-pause-old / user-pause-new / user-pause-after-focus | 再慢速换回 192K，打断期间主动按暂停，源切换与焦点返回都不能覆盖暂停 |
| explicit-play | 用户再按播放，新源恢复，JNI 实际前进 |

每阶段五次采样、至少四秒（环境检查会增加实际间隔），正常流程六十条 JSONL，读取原始 time-pos、pause、idle-active、paused-for-cache、path，
同时读取媒体会话进度和状态。窗口和逐段进度使用 #27 的 EngineProgressProbe；额外断言非零进度锚点、
完整阶段集合、曲目标题，受打断阶段每个样本都检查焦点所有者。
焦点恢复和主动播放还要与前一暂停窗口的最后一条 JNI 进度比较，拒绝从零重新播放或向前跳跃。
证据自检分别注入两种恢复错误；即使恢复后的窗口正常前进、媒体会话也一致，仍必须失败。

C 的预取不能提前完成：初始搜索只返回 B，再通过真实搜索替换队列，检查 C 的请求刚开始才切歌。
插件声明 no-store，每次 C 请求延迟十二秒并记录开始和结束；192K/320K 地址查询参数不同，JNI path 必须换源。
切换搜索时要等待新列表独有的 Hang 出现，再点击 B；B 同时存在于旧 seed 页，单等 B 会在路由传递完成前
点到旧结果。API36 #31 首次因 NDK 下载损坏未编译，重跑后实际通过 Live Update 的五条 JS 基线样本，
但替换队列超时，尚未进入切歌。后续补上述唯一条目等待，超时时把当前可见标签写入 logcat，便于复核。
API36 #32 的可见标签显示进入了完整播放页，确认按 B 标题点击时选中了迷你播放条的同名标题。
改为 `MusicItem` 的完整行标签 `JS Flow B, E2E Artist`；迷你播放条的标签是 `歌曲: … 歌手: …`，明确区分。
唯一条目等待继续保留，用来避免搜索路由尚未更新时点旧结果。没有为了凑队列直接调用 JS 或原生队列接口。
工作流固定已推送的 PR head SHA 取公开测试插件和音频，不把 merge preview SHA 当成可下载的 fixture 引用。

## 避免测试自身制造的问题

插件的普通 JS setTimeout 在应用退后台时可能暂停。因此辅助应用取得音频焦点后，测试把 MusicFree 界面
重新置前，每个受打断样本都断言 MusicFree 前台、辅助应用仍持有焦点。这验证界面操作期间的外部打断，
不是后台计时或模拟实际视频界面一直显示。辅助应用使用自身原生计时器，二十五秒后明确记录释放焦点。
API36 #33 已实际通过前五个完整窗口，随后在音质打断的前台检查失败：辅助应用在 onCreate 中先取得
焦点，窗口稍后才显示，测试此前过早把旧 MusicFree 窗口认作已重新置前。现在先等辅助应用窗口真正
到前台且持有焦点，再启动 MusicFree，保留每条样本的前台和焦点检查；没有放宽检查或改变产品实现。
API36 #34 的前台与焦点检查均正确，但旧源窗口第五次读数已到新源装载阶段。dumpsys 与无障碍读取让
五次采样实际用了约 6.4 秒，加上辅助应用启动，原来的九秒取源余量不够。测试插件改为每次 C 请求
延迟十二秒（仍短于播放器十五秒期限），Jest 与源日志检查同步调整；旧源、新源的完整窗口都保留，
没有跳过最后一次读数或容许窗口混用两个源。测试 APK 的代码未变，可以使用同一缓存 APK 重跑。
API36 #35 通过旧源五次窗口后，等新源进度超时；mpv 日志已显示暂停的新源执行了约 32.2 秒的 seek。
测试原来在打开音质菜单前取进度，产品在实际发起取源时取进度，两者相隔了界面操作时间。
锚点改到已观察到取源开始后立即读 JNI，不拿菜单打开前的位置比较。超时另外打印最后的原始状态与
预期锚点，便于区分路径、暂停、buffering 和位置条件。采样也改为距上一次 JNI 读数至少 1100 ms，
环境检查占用这段间隔，避免再额外叠加一次固定 sleep；每个窗口的五条、四秒下限及环境检查均保留。

每次仪器运行从清空数据后的应用开始。测试结束销毁真实 ReactHost，等待回调成功和播放服务释放，
恢复测试前配置；脚本 EXIT 无论成功失败都强制停止应用和辅助应用。旧的原生样本在清数据前已保存到 runner，
共享导出函数支持显式文件路径，存在性和 JSONL 校验失败不会覆盖之前有效的证据。

Maestro 订阅流程结束后，它的 driver instrumentation 仍占用 UiAutomation。脚本先停止两个 Maestro driver
包，并检查 `dumpsys activity instrumentation` 中已无该 owner，再启动真实 JS 仪器测试。
首次 API36 回归 #29 实际碰到 `UiAutomationService already registered`，新流程没进入点播；原来的38项原生
测试已通过。这个运行不是播放失败或正常场景通过证据。启动失败的仪器日志现在也直接输出到 job log，
即使没有原始样本仍能看见原因。

## 故障对照和自检

第二次独立仪器运行经真实 JS 点播 B。启动补播完成后，卸下同一模块观察器、暂停同一引擎，给服务注入
过期 playing 状态。必须失败在 RAW_STALLED，原始五条样本必须同时证明 JNI 停住而媒体会话投影前进至少 2.5 秒。
脚本接受的不是任意失败：setup 失败、跳过、错测试、样本缺失或其他失败原因均让工作流失败。

新增纯 JVM 策略测试覆盖十二阶段完整性、进度锚点及焦点栈解析。测试插件通过应用真实 Plugin loader 的 Jest
测试验证延迟、quality-specific URL、Hang 和 no-store。Python 的证据自检故意删阶段、冻结正在播放的 JNI、
移动暂停的 JNI、偷换焦点/前台、改曲目、缺读数、伪造仪器结果、让慢速取源变快，必须逐一拒绝。
共享导出自检增加显式文件路径的用例。Android 16 工作流先跑证据自检，再编辅助应用、编原生 APK 和跑设备。
辅助应用编译失败不会忽略。

## 请 Claude 重点复核

1. 反射 JNI 是否确实属于真实 ReactHost，是否有任何替代读数让停住也通过。
2. 正常流程是否始终经真实 JS；预取和缓存是否会让十二秒场景失效。
3. 音质新源是否真的应用、是否保留非零进度，系统打断与用户暂停是否分别被验收。
4. 焦点和前台检查是否能防止测试把普通 JS 后台计时误当成播放器问题。
5. 正常仪器完成与 RAW_STALLED 故障对照是否分别严格核对，setup 失败是否可能被接受。
6. cleanup 是否会残留真实 ReactHost、服务、焦点或覆盖先前导出的原始证据。
7. 工作流路径、fixtures SHA 与 APK 缓存键是否对应实际运行的源码。

## 证据边界和后续方向

本轮不是物理音频输出验证，也没有验证真机锁屏、厂商省电、蓝牙、真实视频应用、永久音频焦点丢失。
普通 JS 插件计时器在后台暂停这一点没有改产品策略；已有 Android 14 锁屏/省电场景继续负责后台期限验证。
没有声称覆盖 FILE_LOADED 那个瞬间发生的打断。所有“持续”结论都是离散采样，约一秒内的瞬态误播未必被捕捉。

项目下一步应依据这轮真实证据决定是否需要产品修复，再安排真实设备的电源和音频路由验收。
目前优先把会话、引擎和用户意图区分清楚，防止绿色状态建立在投影位置上；不为扩充数量而增加同义测试。
如果这轮发现真实问题，单独说明触发条件并补能在修复前失败的回归用例。
