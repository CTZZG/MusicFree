# 冷启动：开屏页首帧同步超时的原因和修法（2026-10-15）

## 结论先说

- **原因查实了。** expo-splash-screen 用 `OnPreDrawListener` 取消绘制来撑开屏页。这样做时，系统给主窗口的首帧同步
  每次都要等满 1000 ms 超时才报 Displayed，开屏页交给应用也跟着晚。
- **修法**：不取消绘制，开屏页撑着时把内容藏起来（hold-hidden），`patches/expo-splash-screen+56.0.14.patch`。
  同步超时没有了（第一次出帧到 Displayed：1005 → 134 ms）。
- **真正的收益比前两轮实验说的小。** 在 Beta 的模拟器（3 核、软件渲染）上，主页那一帧交给系统合成的时刻：
  - 中位数 2494 → 2206 ms，约 −290 ms；
  - P95 3322 → 2411 ms，约 −910 ms；
  - 冷启动追踪的截屏印证了这个时刻（第三轮，Beta #153）。

  前两轮按“开屏页移除”算出的约 −1.5 秒是量错了，见“第三轮”。
- 模拟器上收益被主页第一帧的渲染吃掉了（软件渲染约 0.9 秒）。修之前这段渲染藏在那 1 秒超时里，修之后排在 JS 叫收起
  之后。有 GPU 的真机上这一帧应该便宜得多，收益应更接近去掉的等待（1 秒超时加开屏页交接），但没有在真机上量过。
  反过来，这一帧渲染超过约 1.4 秒的机器上修法可能反而慢约 0.3 秒（推算，见“验证”最后一节），要靠真机检查确认。

工作分支 `claude/sharp-planck-xtfenm`，基线 `feat/mpv-only` 的 `ec8aeaf3`（#38 合并后）。不发 Release。

## 背景

性能基线（`docs/handoff/perf-baseline-2026-10-14.md`）发现，每次冷启动，应用画出主页后开屏页还要盖约 1.6 秒：
- 系统等主窗口同步，等满 1000 ms 超时（`SurfaceSyncGroup: Failed to receive transaction ready in 1000ms`）才报
  Displayed；
- 之后开屏页还要约 0.6 秒才移除。

原因当时没有查实。用户同意做对照 APK 查原因，前提是不破坏开屏页的表现。

## 怎么查的

一个实验 APK，`MainActivity` 按启动 intent 的 `e2eSplashMode` 换开屏页的撑法。端到端第 24 步（`E2E_SUITE=splash`）
在同一台模拟器上轮流冷启动各种撑法，排除机器之间的快慢差别。每次记：
- 应用第一次出帧；
- 系统认为画好（Displayed）；
- 开屏页离开屏幕：系统启动窗口图层消失（轮询 `dumpsys SurfaceFlinger --list`）和应用接手的开屏页移除，取较晚的；
- 开屏页走后露出的空白；
- 第三轮起：开屏页拿掉后的第一帧交给系统合成（`home-drawn`），每种撑法另带截屏追踪一次。

JS 叫收起只改 expo `SplashScreenManager` 里的一个标志，实验用反射读。实验代码在提交 `0ebb3113`（第一轮）、
`d5b8c69f`（第二轮）、`1c8b034a`（第三轮），没有合并；分支上只保留正式修法。

## 第一轮：Beta #146

[运行](https://github.com/CTZZG/MusicFree/actions/runs/38665172125)，APK `0ebb3113`，模拟器 API 34。每种 1 次预热 + 10 次。
单位毫秒，相对启动请求，中位数（P95）。“开屏页离开屏幕”只看到开屏页什么时候从窗口拿掉，看不到渲染线程还欠着的帧
（见第三轮），这一轮和第二轮的这一列都偏乐观。

| 撑法 | 开屏页离开屏幕 | 第一次出帧到 Displayed | Displayed | 开屏页走后空白 | JS 叫收起 |
| --- | --- | --- | --- | --- | --- |
| expo（现状：OnPreDrawListener 取消绘制 + 退出监听淡出） | 3602（3849） | 1006（1014） | 2399 | 0 | 1382 |
| predraw（照 expo 自己实现，核对实验） | 3646（3772） | 1006（1021） | 2447 | 0 | 1432 |
| predraw-system（取消绘制，不设退出监听） | 2710（2960） | 1008（1011） | 2410 | 0 | 1379 |
| condition（androidx `setKeepOnScreenCondition`） | 3568（3692） | 1006（1015） | 2353 | 0 | 1321 |
| none（不撑，开屏页一交过来就淡出） | 1703（1820） | 190（320） | 872 | **407** | 1917 |
| hold（不撑，交过来的开屏页留到 JS 叫收起） | 2811（3070） | 206（302） | 799 | 0 | 2236 |

结论：
- **原因是取消绘制。** 取消绘制的四种撑法（androidx 的 `setKeepOnScreenCondition` 内部也是这样）“第一次出帧到
  Displayed”都是 1006 ms 左右，就是同步超时；不取消的两种只要 200 ms 左右。
- 这是同步本身的逻辑卡住，不是机器慢：Beta #144 和 #153 的追踪里，超时都正好在应用第一次真正出帧之后 1000 ms
  （+1491 → +2492；+1261 → +2262）。渲染慢只会让时间变长、各次不同，不会每次都正好卡在上限。
- **开屏页交给应用也被拖慢。** 取消绘制时，开屏页在 Displayed 之后约 1 秒才交给应用；不取消时约 130 ms。
- `none` 露出 407 ms 空白，不能用。
- `hold` 内容一早就画，和 JS 抢 CPU，JS 叫收起推迟到 2236 ms。

## 第二轮：Beta #147

[运行](https://github.com/CTZZG/MusicFree/actions/runs/38669998228)，APK `d5b8c69f`。新增 `hold-hidden`：不取消绘制，
JS 叫收起前内容设成 INVISIBLE（窗口照常出帧，内容不画），叫收起后内容显示、画出一帧再淡出开屏页。每种 1 次预热 + 15 次。

| 撑法 | 开屏页离开屏幕 | 第一次出帧到 Displayed | Displayed | 开屏页走后空白 | JS 叫收起 |
| --- | --- | --- | --- | --- | --- |
| expo | 2636（3153） | 1005（1014） | 1913 | 0 | 895 |
| hold | 1142（2021） | 146（225） | 520 | 0 | 1084（P95 1956） |
| hold-hidden | 1155（2166） | 164（207） | 527 | 0 | 1097（P95 1203） |

当时据此说主页早出现约 1.5 秒。第三轮表明，这是开屏页从窗口拿掉的时刻，不是主页上屏的时刻。

## 第三轮：Beta #153

修好之后的冷启动追踪截屏（Beta #150、#152）里，开屏页从窗口拿掉了，屏幕上却还是开屏页 1.3–2.3 秒。#152 里开屏页
+2026 ms 拿掉，主线程 +2027 ms 就画了下一帧，主页到 +4.37 秒的截屏才出现。修之前的追踪（#144、#145）里，开屏页一拿掉
主页就出现。主线程画完一帧不等于它上了屏：渲染线程还在画前面的帧（主页第一次画）时，这一帧要排队。

所以 `home-drawn` 改为这一帧画好、交给系统合成时才记（`ViewTreeObserver.registerFrameCommitCallback`），再在修好的
分支上对照一轮。[运行](https://github.com/CTZZG/MusicFree/actions/runs/38686558439)，APK `1c8b034a`，每种 1 次预热 + 15 次：
- expo：打了补丁的 expo，即 hold-hidden，就是这次的修法；
- predraw：修之前的做法（第一轮里和原版 expo 一样）；
- hold：内容照常画，开屏页留到 JS 叫收起。

| 撑法 | 主页交给系统合成 | 开屏页移除 | 移除到交给系统合成 | 第一次出帧到 Displayed | JS 叫收起 | 空白 |
| --- | --- | --- | --- | --- | --- | --- |
| predraw（修之前） | 2494（3322） | 2415（3330） | 85（113） | 1005（1013） | 1004（1773） | 0 |
| **hold-hidden（修法）** | **2206（2411）** | 1323（1442） | 878（1008） | 134（260） | 1301（1410） | 0 |
| hold | 2182（2460） | 1979（2302） | 178（1012） | 143（261） | 1388（2284） | 0 |

逐次看：修法 15 次在 2040–2411 ms，修之前在 2234–3322 ms。修法最慢的一次比修之前的中位数还快，修之前最快的一次也比
修法的中位数慢。

截屏和 `home-drawn` 对得上（每种追踪一次，带截屏开销，比统计里慢）：

| 撑法 | `home-drawn` | 最后一张开屏页截屏 | 第一张主页截屏 |
| --- | --- | --- | --- |
| hold-hidden | +2410 | +2054 ~ +2343 | +2358 ~ +2586 |
| predraw | +2948 | +2461 ~ +2908 | +2968 ~ +3318 |
| hold | +2545 | +2329 ~ +2629 | +2654 ~ +2787 |

读法：
- 修法下，开屏页移除到主页那一帧交给系统合成要 878 ms：主页第一次画的渲染排在 JS 叫收起之后。修之前这段渲染发生在
  同步超时的那一秒里，所以开屏页一拿掉主页就在（85 ms）。前两轮只量“开屏页移除”，把这 0.9 秒漏掉了。
- 修法下 JS 叫收起晚了约 300 ms（1004 → 1301）：窗口出帧、窗口切换和开屏页交接现在和 JS 启动同时进行，在 3 核模拟器上
  抢 CPU。修之前这些都被取消绘制推迟了。
- 两者相抵，模拟器上主页上屏中位数早约 290 ms，P95 早约 910 ms（修之前的长尾来自同步超时之后还要等交接）。
- 三种撑法的 72 张截屏不是开屏页就是完整的主页，开屏页直接换成主页，没有空白或半画好的主页。截屏间隔 0.1–0.4 秒，
  更短的闪烁看不到。

## 选哪种

选 **hold-hidden**（第三轮里的 expo）：
- 和 hold 的中位数打平（2206 对 2182，在误差内），P95 更好（2411 对 2460），JS 叫收起的 P95 好得多（1410 对 2284）：
  看不见的内容不画，就不和 JS 抢 CPU；
- 表现和修之前一样：开屏页盖到 JS 叫收起，收起时主页已经画好；
- 没有开屏页交过来时，内容也一直藏到 JS 叫收起，不会露出半画好的界面（hold 会）。

## 修法（`patches/expo-splash-screen+56.0.14.patch`）

改 expo-splash-screen 的 `SplashScreenManager`（patch-package，和仓库里其他原生依赖的补丁一样）。

**必须从源码编译**：expo-splash-screen 自带预编译 AAR（`local-maven-repo`，`expo-module.config.json` 里有
`android.publication`）。expo 自动链接默认直接用这个 AAR，不编译 node_modules 里的源码，补丁装得上却不进 APK。
第一次只加了补丁，[Beta #148](https://github.com/CTZZG/MusicFree/actions/runs/38673273613) 的数字和修之前一样
（第一次出帧到 Displayed 仍是 1007 ms），这样才发现。
- 所以 `package.json` 加了 `expo.autolinking.android.buildFromSource: ["expo-splash-screen"]`，
  `npx expo-modules-autolinking resolve -p android --json` 里能看到这一项生效；Beta 的构建日志里有
  `:expo-splash-screen:compileReleaseKotlin`。
- 结构不变量审计（`generator/audit-invariants.mjs` 第 6 项，规则在 `generator/lib/prebuiltPatches.mjs`）检查：
  打了 Android 补丁、自带预编译 AAR 的 expo 模块必须写进 buildFromSource。去掉这一项时审计会失败。

补丁改了这些：
- 不再用 `OnPreDrawListener` 取消绘制。`registerOnActivity` 时，如果 JS 还没叫收起，把内容视图（`android.R.id.content`）
  设成 INVISIBLE，窗口照常出帧。
- 系统交过来的开屏页（退出监听）先留着；JS 叫收起（`hide()`）后，内容显示，等窗口画出一帧再淡出、移除开屏页。
  交接比 JS 叫收起晚时，也先显示内容再等一帧。
- `hide()` 可能在 JS 模块的线程调用：标志是 `@Volatile`，显示内容、收开屏页放到主线程。
- 保留 expo 对 API 31–33 的处理（Activity 停下时清掉退出监听）。另外，停下时还留着的开屏页直接移除，避开同样的
  SurfaceControl 问题。
- 同一进程里 Activity 重建时，旧 Activity 留着的开屏页直接移除；JS 已经叫过收起就不再藏内容。

边界：
- 没有开屏页交过来（系统没显示开屏页）时，内容照样藏到 JS 叫收起，和修之前取消绘制时一样看不到内容。
- API 31 以下，androidx（core-splashscreen 1.2.0）自己做开屏页视图，加在 decor（根视图）下面，和内容视图是兄弟，
  内容设成 INVISIBLE 不会连开屏页一起藏掉；同样走退出监听，逻辑相同。这是读 androidx 源码的结论（评审也核对过），
  没有在 API 31 以下的设备上看过。

## 性能基线跟着改

- `first-draw`（`MainActivity`）现在是应用窗口第一次出帧，不再等 JS。
- `home-drawn`（`MainActivity` 的 `HomeDrawnWatcher`）：开屏页（`SplashScreenView`）从窗口拿掉后的第一帧交给系统合成
  的时刻，性能基线以它为“主页出现在屏幕上”。说明：
  - 是交给系统合成，通常再过一两帧上屏；回调在主线程跑，主线程忙时会再晚一点；
  - 只在冷启动（没有 savedInstanceState）、API 31 起记；最多等 15 秒，没有开屏页交过来就到点停，Activity 销毁时也停，
    不会一直每帧检查，也不会在没等到时记一条假的。
- 另加“开屏页走后的空白”（`cold_blank_ms`，应为 0）和“开屏页移除到交给系统合成”。空白是按日志时刻算的（开屏页移除时
  主页标签栏排好版没有），不是逐帧看画面；画面要看冷启动追踪的截屏。

### 不同运行不能比，主页第一帧渲染慢的机器上修法可能不赚

#155 和 #153 的代码路径一样，但那台机器的软件渲染慢得多：开屏页移除到交给系统合成 1676 对 878 ms，JS 叫收起只慢约
12%（1452 对 1301）。#152 的追踪里这段也有约 2.3 秒。所以只能比同一次运行里的对照，不能拿 #155 和 #153 比。

按 #153 同次对照的数推（没有在慢的机器上做同次对照）：
- 修之前，主页第一帧的渲染在 JS 叫收起后马上开始，和约 1.4 秒的同步超时加开屏页交接重叠，只有渲染比这段还长时才露出来；
- 修之后，这段等待没有了，但渲染排在 JS 叫收起之后，而 JS 叫收起本身还晚约 0.3 秒（窗口出帧、交接和 JS 启动抢 CPU；
  #146、#147 里也是晚 0.2 秒以上）；
- 所以设主页第一帧渲染要 R：R 小于约 1.1 秒时修法快（#153 的 R 约 0.9 秒，快约 0.3 秒）；R 超过约 1.4 秒时修法反而
  慢约 0.3 秒（#155 的 R 约 1.7 秒，很可能就是这样）；
- 有 GPU 的真机上 R 应该远小于 1 秒，JS 也未必被拖慢，修法应快约 1 秒。

这只在真机上能确认。真机检查时如果冷启动反而变慢，说明真机上主页第一帧也很贵，应先查渲染，再决定要不要这个修法。

## 没做 / 留给以后

- 只在 API 34 模拟器（软件渲染）上量过。请在真机（尤其 Android 15/16）上看冷启动：开屏页是否照常盖着、收起时有没有
  闪一下空白、是否变快、快多少。
- 模拟器上主页第一帧的渲染要约 0.9 秒，没有查是哪部分贵（软件渲染下的模糊、着色器编译等）。
- 开屏页淡出只在内容画出一帧（主线程）之后开始，不等这一帧交给系统合成。真机上渲染线程还在画时，淡出的头几帧可能看不到；
  没有改，要看真机效果。
- 实验用的第 24 步（`splash.sh`）和 `SplashExperiment` 没有合并；要重做对照，可以从 `1c8b034a` 取（GitHub 上不在任何
  分支，可能会被清理）。
