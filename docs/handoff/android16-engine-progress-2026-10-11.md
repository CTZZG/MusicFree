## 为什么补这一项

`MpvPlaybackService.currentNotificationPosition()` 会从最近一次引擎回调的位置加上墙上时钟差，
Android 16 启用 Live Update 时服务每秒刷新通知与媒体会话。引擎回调停止时，这个投影仍可能向前走。
因此上轮 Android 14 的会话进度检查，不能直接证明 Android 16 原始引擎持续前进，更不能证明扬声器出声。
现有 `LiveUpdateNotificationStyleTest` 通过手动服务回调检查通知样式，未装载真实音频。

没有改掉产品的进度平滑：它有用户体验上的用途，目前没有证据表明需要删除。
本轮补独立观测，先让验证能区分“投影在走”和“引擎在走”，避免为通过测试而改变播放器行为。

## 做了什么

### 独立检查器

`EngineProgressProbe.kt` 的输入包括单调时钟、JNI `time-pos/pause/idle-active/paused-for-cache/path`
和 `MediaControllerCompat.playbackState` 的位置、状态。原始字段没有服务缓存或 JS 缓存回退。

- 每个窗口至少五次采样，跨度至少四秒；相邻间隔为 0.75–5 秒，过短、逆序或严重采样迟延拒绝。
- 播放时逐段要求引擎与媒体会话都前进。原始进度每段至少达到实际间隔的 25%，上限约 1.75 倍加 0.25 秒。
  这是 1× 本地测试音频的容差，不是任意播放速率的通用检查。
- 原始位置必须有限、非负，各状态不能缺失；不能暂停、空闲或缓冲，实际加载路径必须匹配测试文件。
- 会话状态必须是播放，投影和原始位置差不超过 1.5 秒。暂停时原始位置变化不超过 0.15 秒，
  会话位置变化不超过 250ms，状态也必须暂停。
- 没有用窗口首尾的总进度掩盖中间某段停滞；失败保留原始样本和明确原因码。

最初九项 JVM 测试覆盖正常容差、原始停滞、单段停滞、缺失/非有限位置、错误曲目/窗口、
引擎/会话状态不符、投影漂移、会话停滞、seek 式跳跃和暂停时的两个时钟。
部分方法包含多组输入，九是测试方法数，不能当成九个独立用户功能。
Claude 复核后的补充让检查器测试增至十一项，详见下方补充记录。

### 真实原生流程

`LiveUpdateEngineProgressTest` 现场生成 90 秒单声道 PCM WAV，由真实
`MpvPlayerModule.initialize/loadAndPlay/pause/resume` 装载，保留正常 AudioTrack/OpenSL ES 输出配置。
读取的 JNI 对象就是该模块持有的 `mpvInstance`，通过测试侧反射取得，避免给产品增加调试端口。
这个字段改名会使测试失败，需同步维护；不会静默换成另一个播放器实例或缓存值。

`NativePlaybackTestContext` 只接收并丢弃发往 JS 的事件；额外 JS/native 依赖会明确失败。
服务和原生回调真实运行，但没有 React 页面、Metro、插件、联网取源或 JS 切歌事务。

三个设备测试：

1. 播放：五个原始样本持续前进，同时通知确实采用 Android 16 `ProgressStyle`。
2. 暂停、恢复：暂停窗口两个时钟保持不变，恢复窗口重新前进。
3. 负面对照与恢复：真正暂停引擎、卸下模块观察器，在服务上注入一次过期的 `playing` 状态。
   确认 Live Update 自己投影的进度至少前进 2.5 秒，同一个播放检查必须以 `RAW_STALLED` 拒绝。
   随后挂回观察器、恢复播放，再检查正常窗口。

负面对照是**测试注入的过期服务状态**，不是 CPU 挂起、真实网络阻塞或产品中已复现的同步缺陷。
JUnit 为“正确拒绝故障”判通过，流水线不需要留下故意红色的分支检查。
清理会撤销模块回调/重试、销毁 JNI、停止服务、清掉 Live Update 开关和音频持有状态，并删除测试音频。

### CI 和原始证据

在原有 API 36 代理与订阅工作流接入两个测试类，没有另起大型构建链。
原有逐测试完成状态核对继续生效：非零状态、跳过、缺类、未完成都拒绝。
另要求 `playing/paused/resumed/negative-stale-projection/recovered-after-control`
五个阶段各五条 JSONL 样本。重跑前清掉旧样本；失败时也尽量导出部分样本，不能拿旧文件顶替。

附件为 `proxy-subscription-<run_id>`，包含仪器测试日志/摘要和 `engine-progress-samples.jsonl`。
样本记录单调采样时间、原始位置/状态、会话位置/状态以及曲目匹配结果，不含用户插件地址。

## 项目判断与下一步

当前应继续补行为证据，而不是增加播放器补偿分支。暂停意图、超时事务、缓存、原生服务的职责已逐步明确，
后续修改应遵守它们的边界，避免通过更多延时、自动重试掩盖状态错误。
同样，已有设备测试值得保留，但需要把“环境成立”“行为成立”“观测可靠”三层分别证明。
这轮补的是观测可靠性，没有宣布 API36 的整个播放器已经验收。

下一步优先级：

1. 把原始观测接到 API36 的实际 JS 切歌、慢速音质切换和系统打断场景，必要时扩展 API14/API16 对照矩阵。
   不要直接用 `getPosition()` 的缓存回退当原始证据；也不要给产品暴露不受限的诊断入口。
2. 真机矩阵覆盖厂商省电、后台受限、进程被杀、密码/指纹锁屏、蓝牙，以及真实视频/Telecom 来电。
3. 如果要证明持续出声，另做可验证的音频输出观测；原始时间前进和活动 AudioTrack 都不足以证明物理声音。

下载首次写盘失败、迁移删除/清空的设备注入，以及 Android 14 锁屏、省电检查，已在上轮合入并有记录。
本轮没有重复那套全量测试，也没有把其结果扩张为 Android 16 或真机结果。
