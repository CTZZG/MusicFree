## 为什么补充

Claude 指出的可选缺口成立。PR #30 的 API36 #41 中，最后有效旧源读数与首次有效新源读数相隔
1079 毫秒，记录的最后一次轮询间隔为 170 毫秒。它没有保留中间各次间隔，因此不能据此证明
整个过渡都在连续采样，也不能断言那次运行真的出现了主线程停顿或产品回退。

旧策略只拒绝首次新源读数前的长间隔。如果旧源最后一次读数之后出现空档，之后的卸载/装载
轮询恢复正常，最后间隔短也会放行。这会削弱旧位置作为停止位置的证据。

## 怎么改

`SourceTransitionProbe` 在最后有效旧源读数之后累计每次轮询间隔的最大值。
即使该次位置缺失、为零、NaN、idle/buffering，或地址不一致，这次轮询的间隔也仍然计入。
只有新的有效旧源读数才能刷新旧位置锚点，并清空其之前的间隔历史；无效读数不能清空历史。
首次有效新源读数到来后，最大间隔超过 250 毫秒就以 `TRANSITION_WINDOW` 拒绝测量。
已有首值保留、路径前后核对、JNI 读取后时间戳和跨源回退判断保持生效。

总卸载/装载时间可以超过 250 毫秒。限制的是期间每次采样间隔，连续观测的长过渡不会被误判。
在新源到来时才判断累计最大值，因此旧源仍播放时一次长间隔之后取得的有效新锚点仍可使用。

仪器测试在五条新源窗口中输出相同的 `maxPollGapMs`，同时保留原来的 `pollGapMs`。
Python 要求新字段为整数，满足 `0 <= pollGapMs <= maxPollGapMs <= 250`，且最大间隔不能
超过旧读数到新读数的总时间。遗漏、类型错误、超过限制或前后记录不一致均拒绝。
十四阶段七十条正常样本和五条冻结对照的数量不变。

## 请 Claude 复核

1. 累计范围是否从最新有效旧源读数开始，所有中间无效读数是否仍计入。
2. 新锚点刷新能否丢弃它之前的历史，同时无效旧源读数不能清空历史。
3. Kotlin 是否拒绝中间长空档，而非只看最后间隔；首个新源结果是否继续不可覆盖。
4. Python 是否要求并核对最大间隔，250 毫秒边界与总过渡超过 250 毫秒是否分别正确处理。
5. 本轮原始证据里的最大间隔、最后间隔、跨源位置是否与最终提交对应，设备是否重编译了测试 APK。

## 限制与后续方向

最大间隔由 Kotlin 采样器累计，Python 可独立检查字段约束，但 JSONL 没有逐条保存所有中间轮询，
因此 Python 不能从原始中间轨迹重新计算最大值。累计实现由 JVM 回归和删判断对照约束。
仍是离散 JNI 采样，无法给出真实 seek 动作的毫秒级硬保证，也没有验收音频输出。
250 毫秒空档属于测量不足；不能直接称为产品回退，也不应为了让运行变绿而放大容差。
这项完成后，优先推进可复现的用户问题及已有设备验证待办，避免继续为测试数字改动播放主流程。
