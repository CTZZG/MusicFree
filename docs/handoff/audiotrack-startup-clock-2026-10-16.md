# AudioTrack 启动进度修正与 0.11.5 验收

## 问题与范围

版本准备 PR #41 的 Android 16 #77（run `38867597369`）触发真实
`SOURCE_REWIND`：旧源最后读数及原生捕获目标都是 `90.66106863696946` 秒，
首个新源读数是 `90.32854196796826` 秒，差 `-0.332526669` 秒。15 次过渡轮询的
最大间隔只有 93 ms，未发生此前的采样间隔问题。75 个原生用例通过不等于整个
工作流通过；该次真实 JS 仪器失败，后续 UI 和冻结引擎控制没有执行。

本修复独立于六文件版本准备。它不改 JS 换源目标、原生位置捕获、暂停意图、
音频焦点、音频后端、共享解码库或测试的 250 ms / 0.25 s 门限。

## 本地定位

使用 API 28 软件模拟器、真实已装应用的 MPVLib/JNI 和同一首 MP3，去掉 JS、
服务和通知估算仍能复现。`absolute+exact`、等待 seek/restart、`loadfile start`
以及关闭 gapless 各自仍有超过门限的读数，未作为产品修复采用。

同版 mpv 0.41.0 重新编译的旧逻辑带诊断日志作对照：6 次换源中 3 次越过
0.25 秒，最差 `-0.361095760` 秒。日志抓到尚未提交音频时，AudioTrack 已给出
314 ms 估计硬件延迟；提交 2400 / 16000 Hz 帧时则扣除 464 ms。这会把输出
时钟算到本次恢复起点之前。

只加入启动延迟边界、保留相同诊断日志的对照，6 次有效窗口均未越限，最差
`-0.065504910` 秒。此结果是局部候选验证，不冒充最终库验收。去掉诊断日志后，
原小探针有一轮在固定 1.2 秒截止前仍处于 seek，未取得有效样本；这轮没有被计作
通过。正式新增回归要求完整有效观察窗口，缺失或间隔过大直接失败。

上述本地软件模拟器不代替 Android 16 或真实手机，也不证明物理音频输出。

## 产品修补

`native/mpv/audiotrack-startup-delay.patch` 与 `audiotrack_latency.h`：

- 仅在创建或 flush 后、PCM 尚无有效设备时间戳时，将估算延迟限制为自 reset
  以来已提交音频的时长。不是在 JNI 读数上套固定下限或替换原始读数。
- 获得有效时间戳或已提交两秒音频后停止边界处理；两秒沿用原驱动最大延迟。
  后续 32 位帧计数回绕不会重新启用启动处理。编码音频透传不受影响。
- warmup 状态只由 AO 工作线程读写；reset 通过原子请求通知它重新开始，避免
  上一轮工作线程结束时清掉新 reset 的状态。没有新增线程、锁或自动播放命令。

四种架构的 libmpv 按固定源码和 NDK 27.1.12297006 / API 26 重建。仅四个
`libmpv.so` 被替换；共享 FFmpeg、JNI、Java 类和 AAR 中的 C++ runtime 字节保持。
详见 `native/mpv/README.md`、`sources.lock.json`、`bundle.json` 和重建脚本。

## 回归设计

- 主机 C 测试直接编译同一 helper，覆盖初次提交、flush、有效时间戳、透传、
  稳定态和计数回绕。删除启动边界的变异必须触发断言失败。
- `AudioTrackSeekClockTest` 用真实 MPVLib 和 AudioTrack，两种目标各换源三次。
  每轮至少十个有效 raw 样本、观察至少一秒、间隔不超过 250 ms，最差位置不低于
  实际捕获目标减 0.25 秒，且确实前进。另检查进度不会超过真实经过时间加容差。
  `check-seek-clock.py` 根据 JSONL 独立重算；不以仪器返回码替代样本完整性。
- 原有真实 JS 转场、暂停与焦点、慢加载、实际页面按钮、冻结引擎和全量模拟器
  步骤继续保留。新仪器源码改变必须真正编译；缓存命中会按实际记录。

## 最终结果

2026-10-17 本地已完成最终四架构库及完整窗口对照：

- 四个 ELF 均为对应架构、16 KiB LOAD 对齐、相同 SONAME；与原包保持相同
  DT_NEEDED 和 54 个 mpv 客户端导出。对原 FFmpeg / NDK 27 API 26 的导入检查
  没有缺失符号，最终库不含临时诊断日志。AAR 清单独立核对通过。
- SDK 36 实际编译新的 Android 仪器 Kotlin，并生成测试 APK；Debug Gradle
  单测实际执行，本地生成的 XML 为 25 套、138 项，failure/error/skipped 均 0。
  编译时 Java/JNI API 与原 AAR 字节相同；运行时使用下述最终 libmpv。
- API 28 软件虚拟机安装文件哈希已独立核对。相同测试 APK
  `4c4d1121c112508b97dfeb460d906b430bd9ae873aa5460fe00b930be34c66e3`
  在原应用上第一轮即报 `SOURCE_REWIND`：36 个有效样本、1186 ms 观察窗，
  最差 `-0.369965840` 秒，最大间隔 60 ms。不是 setup 或采样过慢失败。
- 仅替换最终 x86_64 libmpv 的本地诊断应用上，1 个 JUnit 方法内六轮全部完成，
  共 191 个有效样本，最差 `-0.075676940` 秒、最大间隔 207 ms；独立 Python
  重算通过，所有窗口至少一秒且满足原 250 ms / 0.25 s 限制。该诊断 APK
  不是正式打包结果；已逐项核对除签名外只有 libmpv payload 改变，并确认
  库字节与最终四架构 AAR 的 x86_64 项相同。
- 前次冷启动软件 VM 的安装超时及退出后残留锁保留在本地记录；该阶段未进入
  仪器，不作为产品测试失败或通过。恢复现有热快照后正常完成安装和对照。

主机 C 测试及删除边界的变异、四架构 payload 检查、证据检查器 21 项自测通过。
本地完整质量门实际通过：189 套 / 1397 Jest、48 generator、1257 layout，
ESLint 0 错误 / 216 警告，TypeScript、静态审计和补丁重放通过。未构建 Release
manifest 的对应审计分支按设计跳过，不写成 Release manifest 已验。
CI / Android 16 / Beta 的最终结果在独立修复 PR 中按实际运行追加，不以本地
API 28 结果替代。尚未据此创建 v0.11.5 标签或正式发布。

用户此前反馈冷启动、加载时暂停和视频打断恢复正常，范围为此前候选；不把该反馈
冒充对这次新 AudioTrack 库的独立真机测试。物理音频、厂商后台限制和新增库的真机
定量表现仍未系统验收。
