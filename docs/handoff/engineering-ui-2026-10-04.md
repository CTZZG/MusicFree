## 2. Codex 做了什么，为什么这样做

### 2.1 原生变更检测：删除和重命名也影响构建

Git 检测到重命名时，普通 `--name-only` 输出可能只有新路径。将 `android/PlaybackState.kt` 移到 `docs/PlaybackState.kt` 后，新路径不匹配原生目录，但原生工程已经少了一个文件。按换行拆文件名也会受路径转义、中文或文件名内换行影响。

我改为 `git diff --no-renames --name-only -z base HEAD --`：重命名按旧路径删除、新路径新增处理；NUL 分隔保留原文；日志以 JSON 引号转义显示特殊路径。手动运行、新分支、无法解析比较基准时，沿用保守规则：运行原生测试。

入口：[detect-native-changes.mjs](../../generator/detect-native-changes.mjs)；路径和基准规则：[nativeChanges.mjs](../../generator/lib/nativeChanges.mjs)。`android/`、`patches/`、依赖清单等已纳入检测；新增原生构建入口时应同步检查规则。

新增 [nativeChanges.integration.test.mjs](../../generator/lib/nativeChanges.integration.test.mjs) 的 4 项测试使用真实临时 Git 仓库、检测脚本及 `GITHUB_OUTPUT`，覆盖移出原生目录、特殊文件名、纯文档跳过、错误基准仍运行。

理由：**质量门必须保证该运行时真的运行。** 多花几分钟 Gradle 时间，比漏掉原生删除造成的构建问题更可接受；只测试路径正则覆盖不到 Git 的真实输出格式。

### 2.2 ESLint 基线：检查失败不能改变判断标准

Claude 已建立按规则计数的基线，但 `--update` 的写盘顺序有缺陷：先写较低统计、再发现解析错误或其他规则回归，命令虽然失败，原基线已经改变。解析错误容易让“统计到的警告变少”，这不代表代码改善。

我将顺序改为：读取结果 → 计算候选基线 → 检查全部错误和规则回归 → 成功后写入。任何失败都保留原基线字节。

实现：[eslint-ratchet.mjs](../../generator/eslint-ratchet.mjs)。新增 [eslintRatchet.integration.test.mjs](../../generator/lib/eslintRatchet.integration.test.mjs) 的 3 项实际 ESLint CLI 测试，证明语法错误不写盘、一个规则减少不能抵消另一规则新增、合法改善可写入并通过下一次检查。

门禁修复时为 225 warnings；本次榜单改版移除一处内联样式警告，当前为 **0 errors、224 warnings、12 条规则**，已提交更低基线。本机制允许同一规则内警告位置变化，不能发现所有“修一条又新增一条”的抵消；实际 diff 审查仍必要。后续可评估改动文件的增量检查，暂时不必引入脆弱的行号指纹系统。

### 2.3 底栏：从压缩占用改为平衡留白与触摸

用户最初认为底栏接近屏幕五分之一，希望减少占用。我将两栏压到 50／52 dp，总预留 116 dp。Beta #70 真机截图反馈这组参数过紧：满足不溢出和最低触摸尺寸，并不代表封面、两行文字和导航标签比例舒服。

随后用户提供 `13262.jpg`（DS One）和 `13261.jpg`（MusicFree）。我参考 DS One 的封面、文字和留白比例进行修正；截图用于比例参考，未把图片像素当作设备 dp 精确测量。

| 参数 | 起点 | Beta #70 | 当前 856859f |
| --- | ---: | ---: | ---: |
| 播放条高度 | 62 | 50 | **60** |
| dock 高度 | 64 | 52 | **60** |
| 两栏间距 | 10 | 6 | **8** |
| 离底部安全区的悬浮距离 | 10 | 8 | **8** |
| 总预留，不含系统安全区 | 146 | 116 | **136** |

单位均为 dp。当前封面 44 dp，上下各留 8 dp；播放／队列按钮触摸区 48 × 48 dp、图标 26 dp。dock 内边距 6 dp、导航项高 48 dp、图标 24 dp、标签字体 11 dp／行高 14 dp；歌曲文字和进度条间距适度恢复。

同时调整内部元素，是因为只增高外壳会留下偏小的封面和图标。尺寸集中在 [layout.ts](../../src/components/musicBar/layout.ts)，内容预留由 [layoutPolicy.ts](../../src/components/musicBar/layoutPolicy.ts) 计算；原有玻璃胶囊、播放信息、切页和手势继续使用。

首页两栏总预留 136 dp；二级页面只有播放条时预留 68 dp；首页无歌曲时只为 dock 预留 68 dp；键盘出现时两栏收起。安全区由宿主另行处理，避免为一张截图硬编码底部坐标。

相关文件：[MusicBar](../../src/components/musicBar/index.tsx)、[MusicInfo](../../src/components/musicBar/musicInfo.tsx)、[HomeTabBar](../../src/pages/home/components/tabBar.tsx)、[布局规则测试](../../src/components/musicBar/__tests__/layoutPolicy.test.ts)。当前 136 dp 仍等待用户对 Beta #71 的真机验收；下一步在同一手机比较，避免仅凭数值反复缩放。

共用大标题和搜索独立大标题均由 34 改为 28 dp，行高 41 改为 34 dp。这样给内容和右上角操作更多空间，同时保留标题相对 16 dp 正文的层级。

### 2.5 资料库歌单列表模式

右上角在导入、新建旁增加切换按钮，图标表示下一种视图，并提供简体中文、繁体中文和英文读屏标签。`library.playlistView` 保存 `grid`／`list`，未设置或其他值按网格显示，兼容原有使用习惯。

列表采用 48 dp 封面、最多两行歌单名、歌曲数量和进入箭头，适合窄屏长名称。偏好通过现有 `AppConfig` 写入并订阅，首次点击生效，重新进入恢复选择。两种模式共用 `SheetItem` 的打开、长按确认删除、“我喜欢”保护和排序；网格宽度扣除左右安全区。

我复用现有订阅和同一个条目组件，让两种视图共享数据与行为。另建列表数据或删除流程，容易产生切换后顺序不同、收藏保护遗漏等维护风险。

实现：[Library](../../src/pages/library/index.tsx)；类型：[config.d.ts](../../src/types/core/config.d.ts)；新增 [squares-2x2.svg](../../src/assets/icons/squares-2x2.svg)，同步生成图标入口。

新增 [playlistView.test.tsx](../../src/pages/library/__tests__/playlistView.test.tsx) 的 5 项交互测试，使用真实 `useStoredJson` 订阅和测试存储，覆盖首次切换、卸载再挂载恢复、两种模式打开相同歌单、删除确认及收藏保护。真正杀进程后的落盘恢复仍需设备检查。

### 2.6 榜单参考酷狗概念版：提高密度、减少卡片分割感

用户对比 `13268.jpg`（酷狗概念版）和 `13266.jpg`（项目当前榜单），希望后者更紧凑、协调。原实现最小格宽 140 dp，普通手机只有两列，每张方形封面下还有白色标题底座与序号，导致同一屏显示的榜单偏少。

普通卡片现在为三列、14 dp 圆角方卡，标题放在卡片内，最多两行，使用深色半透明底保证图片上白字可读；移除序号与外部白色底座。无封面时采用彩色底卡。页边距 16 dp、格间距 12 dp、组间距 24 dp，宽屏再按可用空间增加列数。

如果 `getTopLists` 返回的条目已有有效 `musicList`，显示横向卡片：左侧榜名与最多三首歌曲，右侧 72 dp 封面。只展示插件已经返回的歌曲，不为列表另行请求所有榜单详情。LXD 等只返回标题和封面的来源使用方卡；不能用虚构歌曲填出参考图里的预览。不同类型混排时保持插件原顺序，点击仍传递原榜单对象与插件 hash。

网格宽度改为测量实际面板，旋转后重新测量。测试发现 363 dp 场景下，`onLayout` 的像素取整可能使计算宽度略大于 Yoga 内部空间，第三张卡片因此换行；格宽向下取整后稳定为三列。

实现：[TopListItem](../../src/components/mediaItem/topListItem.tsx)、[BoardPanel](../../src/pages/topList/components/boardPanel.tsx)、[topListGridLayout](../../src/pages/topList/components/topListGridLayout.ts)。新增 [交互测试](../../src/components/mediaItem/__tests__/topListItem.test.tsx) 4 项，验证两类卡片打开原榜单、最多三首有效歌曲、异常预览元数据和无标题／封面回退；[布局测试](../../tests/layout/topLists.layout.test.mjs) 16 项覆盖中英文、深浅色、320／363 dp、窄于窗口的 300 dp 面板以及 704 dp 横屏面板，检查文字、封面、顺序排布和不重叠。

此次修改经过本地质量门，卡片观感仍需新版 APK 真机确认。优先检查原 LXD 的收听榜、资料库榜、发现分组，再选择带预览数据的来源验证横卡。

## 4. 我对项目当前阶段的判断

### 4.1 保留现有基础，把模块之间的边界做可靠

已有播放协调器、搜索会话、下载最终化日志、本地音乐规则和测试。页面通过业务入口、纯策略脱离 React／原生依赖、core 不依赖 pages 等方向合理。判断来自入口源码、架构说明和测试结果，并非对全仓库每条路径的认证。

更值得投入的是用户意图与迟到的异步结果、插件返回与应用解释、native 状态与 JS 页面、持久化与订阅更新、可用区域与文字尺寸。最近多个问题发生在“单个公式或模块正确，组合后失效”的位置。

建议沿现有 Jotai、external store、TrackPlayer 门面逐步收口接口。当前证据不支持同时换状态库、重写播放器和重做所有页面；那样很难判断回归来自哪个变化。

### 4.2 第一质量指标是能稳定听下去

视觉一致性有价值，核心路径优先级更高：开始播放、快速切歌、切音质、锁屏／后台、断网恢复、下载后可用。JS 测试验证协调规则，JVM 测试验证原生辅助逻辑，还缺少连接两者的设备证据。

如果只能安排一项设备检查，我会选：**冷启动恢复歌曲 → 播放 → 快速切歌与切音质 → 锁屏／后台 → 回前台，确认界面、声音、通知、队列一致。** 这更可能发现影响“能否继续听”的组合问题。

### 4.3 放得下和好用需要分别验证

116 dp 底栏通过几何和触摸检查，用户仍觉得过低。几何测试适合阻止文字被裁和控件重叠；比例、留白、玻璃对比度与点击观感需要真机判断。

建议形成少量共享约定：28 dp 标题、16 dp 常规页边距、统一间距和触摸区域、统一安全区与底部预留策略。竖横屏、大字体按实际容器安排空间；公共尺寸变动记录受影响页面和设备结果。

### 4.4 插件状态和失败原因应让界面自然获得

插件带来外部网络、数据格式、启停和配置变化。当前插件数组、元数据、事件与 enabled revision 是多条更新渠道；只依赖数组引用容易遗漏启停变化。笼统诊断又容易把鉴权失败理解成音质不可用。

给 UI 提供稳定状态快照，让订阅者自然获得更新；错误沿已有分类传播。运行实例与元数据快照分开，避免冻结实例导致插件内部失效。仓库目前按可信代码执行插件；快照解决一致性，不提供执行隔离。改变信任模型需单独设计真实隔离环境。

### 4.5 质量门应证明能拒绝真实回归

本轮两处门禁都增加失败输入的 CLI 测试。后续同样关注真实入口、生命周期和跨模块行为，避免测试只重复公式。测试数量是覆盖线索，不是发布充分条件。

APK 打包、自动测试通过、真机功能通过、用户视觉认可分别记录。Beta #71 自动化成功也不能替代用户对 136 dp 底栏的确认。

### 字体策略

正文和内容标题以跟随系统为目标。紧凑固定控件有实际空间限制时才局部采用 1.5 倍上限并说明原因。处理顺序：容器增长／换行 → 省次要行 → 必要局部上限 → 裁剪兜底；关键正文可读性优先。

第一批接回播放页和插件变量表单，随后推荐歌单。资料库与底栏已有几何测试，也可按 scope 逐步接入，但测试需与应用使用相同开关。

（Claude 补记，2026-10-05）歌词页已经定下：PR #9 让歌词只按歌词自己的字号设置显示、不再叠加系统字体，并加了三个更大的档位，见 architecture.md 的字体一节。

（Claude 补记）两套缩放叠加的是**歌词页**，不是迷你歌词：迷你歌词是固定高度的预览窗口，`b12fc4c` 起不跟随系统字体；歌词页的字号来自自己的设置（`lyric.detailFontSize`），歌词行又直接用 `Text`，同时跟随系统放大。迁移歌词页时要定下以哪个为准。

### 插件快照策略

先统一读取和订阅入口，再迁移消费者。快照包含版本、插件标识、启用状态、排序及必要元数据；采用 `useSyncExternalStore` 或与现有存储等效机制，无变化时 `getSnapshot` 返回相同引用，变化时发布新快照。

运行实例独立且可变，不深冻结 `Plugin.instance`。先在一处页面证明启停即时更新，再扩至首页发现、搜索来源、推荐歌单，最后处理兼容通知渠道。入口：[pluginManager](../../src/core/pluginManager/index.ts)、[enabledRevision](../../src/core/pluginManager/enabledRevision.ts)。

### 测量与预算策略

竖屏保留真实测量以适应未知内容；固定控件共享的小区域采用明确预算以减少首帧变化。共同依据是实际容器，度量和样式共享，必要时采用保守首帧占位。不要为了形式统一，把全部竖屏测量替换成手写字高公式。

### 支持范围与包体

Gradle `minSdkVersion=24`，libmpv 要求 API 26，manifest 强制合并；API 24–25 能安装不代表能播放。需要先形成产品支持结论，再改声明。

默认仍打包 `musicfree-media3-ffmpeg-decoder` 遗留 AAR，开关 `musicfreeEnableNitroFfmpeg`。移除前检查引用、构建产物和播放格式，本轮未评估收益或删除。iOS 目录保留，但当前分支无 iOS 构建验证证据。事实以 [architecture.md](../architecture.md) 和源码为准。
