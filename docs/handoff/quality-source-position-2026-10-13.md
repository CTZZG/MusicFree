# 换音质：原生替换时捕获恢复位置

本轮分支 `codex/quality-replacement-position-20261013` 基于 PR #34 的 `18f43d50`。PR #34 只调整采样，本轮单独修改产品换音质流程，便于比较和复核。PR #33 下载代码没有加入本分支；没有合并、发版或修改版本号。

## 问题与证据

主线已经在等插件返回之后重新读取进度，修复了取源等 12 秒就退回 12 秒的问题。但重新读取到原生实际 `loadfile replace` 之间，旧源仍在前进，桥接和主线程排队会使恢复目标过时。

Android 16 #46 在 PR #34 `18f43d50` 上失败：旧源最后有效位置 75.137484 秒，实际 hr-seek 目标 74.737051 秒，首次新源读数 74.496846 秒；完整过渡的最大采样间隔只有 98 毫秒，异常读数前后 seeking 均为 false。旧源与实际恢复目标相差约 0.400 秒；目标与首次新读数额外约 0.240 秒差异尚未完整解释。这些不是物理出声测量。

## 实现及理由

- 只有换音质调用 `setTrackSource` 时请求位置保护。正常点歌、上下首与冷启动保留原装载行为。
- `loadQueue` 向原生传入 `preservePositionFallback`。此前 JS 取得的进度仍用于原生无法读到有效位置时的兜底。
- `MpvPlayerModule.loadAndPlay` 在主线程的同一次操作中，完成元数据处理后、紧邻实际 `loadfile replace`，先暂停旧源，再读取其真正停止位置。暂停为换源内部操作，不改变用户播放意图，也不清除外部暂停/系统打断的拦截。
- 只捕获相同媒体身份、匹配实际引擎路径的旧源进度。不同媒体不贡献位置；缺失、失败、负数或非有限值使用兜底，合法零值保留。
- 连续换音质时，上一个新文件可能还没装好，原始位置暂时为零。此时保留它最新的 `PendingSeek` 目标，包括用户后来的拖动到零，不能把临时零当成真正的播放位置。
- 捕获的目标绑定到新装载 generation，进入现有 `PendingSeek`。`FILE_LOADED` 先应用目标，再允许自动取消暂停；用户装载期间的新 seek 覆盖该目标，旧 generation 不会用于新文件。
- 原生 Promise 返回实际安排的恢复位置，适配器转交给 TrackPlayer，更新进度持久化和显示。JS 不再随后用旧的请求位置执行一次 seek，避免把原生刚捕获的进度覆盖掉。原生未返回有效目标时，JS 保留旧的兜底路径。
- 用户暂停及系统焦点规则继续由已有 `PlaybackIntent`、`PlaybackHold`、`PendingUnpause` 控制。未更改 250 毫秒采样上限、0.25 秒连续性容差或证据检查器。

## 回归验证

1. `interruptionDuringLoad.test.ts` 使用真实 TrackPlayer、真实 MpvPlayerAdapter，模拟原生边界排队 400 毫秒：旧源从 30 播到 30.4 后才替换。新代码保留 30.4；同一测试在未改产品的 `18f43d50` 独立工作区上失败，Received 30。不是初始化或超时失败。
2. 既有慢取源、暂停、临时焦点归还、拖回零/10、无效位置、歌曲变更及前一音质提交等待的测试继续执行；新增真实路径的连续音质装载用例。
3. 适配器测试约束原生目标 0/30.4 能转交、无效目标不宣称已恢复、普通点歌不请求位置保护。
4. `SourceReplacementPositionTest` 约束先暂停后读、不同媒体、合法零、无效/失败读取、暂停失败，以及前次装载的待应用位置。`PendingSeekTest` 补充不消费的窥视、最新目标覆盖、跳转应用前阻止自动恢复等状态。
5. 本地独立 Kotlin/JUnit 编译上述真实生产辅助类及测试：15 项通过。刻意删掉暂停步骤时，八项捕获测试中两项失败；原生产文件未做该变更。未在本地编译完整 Android 模块或仪器源码，因为本环境没有 Android SDK；那部分必须等待 CI。
6. Android 16 新增真实原生控制：持住 main looper，把同媒体换源排进队列，继续读取真实引擎，确认旧源在排队期间推进；释放主线程后，原生返回的目标必须包含这段进度。新 generation 必须真实加载并恢复到该位置，保持暂停后用户能恢复播放。测试的 finally 释放主线程并等待读数线程结束，既有清理仍销毁引擎和服务。
7. 新增原生辅助类及 PendingSeek 测试显式加入设备执行清单，缺失/跳过仍由清单校验拒绝。设备结果、最终完整质量门数字及原始样本核对记录在 PR 描述，当前不可用旧 #46 失败或 Beta #134 成功代替。

## 请复核的重点

- 停止与读取是否确实发生在原生实际换源边界，JS 是否不再用旧位置覆盖捕获结果。
- 同媒体/实际路径校验、前一 generation 的待应用目标以及用户后来 seek 的优先级是否正确。
- 自动取消暂停是否等待恢复位置应用，同时继续尊重用户暂停和临时系统打断；普通点歌和冷启动是否不受新请求字段影响。
- 设备控制是否真正排队、读取真实引擎并确认新的 generation 已加载，而非仅检查 Promise 或服务推算进度。
- 最终 Android 16 的正常 70 条、冻结 5 条及 RAW_STALLED 控制是否完整；第一新源读数和全部中间采样空档仍必须通过原门限。

本轮设备验证仍需核对实际结果。不同录音的备用来源时间轴、物理音频输出、真实设备省电，以及最终加入 PR #33 后的组合验证，不能由本分支的单独结果推定。

### 已修正的 P3 测试缺口

独立复核发现，400 毫秒排队用例的替身只 await 原生加载实现，没有返回它的恢复位置；最后模拟 FILE_LOADED 的 seek(30.4) 掩盖了此前额外的 JS seek(30)。刻意让产品代码忽略原生恢复结果时，原有 17 项仍全部通过。

现在替身返回原生结果，并在 FILE_LOADED 前断言没有 JS seek、之后断言只发生一次模拟恢复。同一强化用例在当前产品实现上通过，在忽略原生结果的错误版本上因额外 seek(30) 失败。该实验没有修改已提交的产品实现。修正后相关 TrackPlayer/适配器测试 55 项通过，TypeScript 与目标文件 ESLint 通过。
