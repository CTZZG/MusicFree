## 代码复核发现及修正

### 1. 崩溃诊断导出漏遮凭据（P2）

`redactCrashText` 原来会保留 `https://user:password@host/path` 的用户信息，也匹配不到异常文本里 JSON 形式的 `"Authorization": "Bearer ..."`、Cookie 等字段。用户复制诊断时可能把这些值带出去。

修正：删除 URL 用户信息中的原值，遮掉引号包裹的凭据值，并让线程名、异常名、原生帧文本同样经过导出脱敏。正常主机/路径和非敏感字段保留。没有改变本地原始崩溃存储、上传任何记录或增加遥测。

新回归测试在原 v0.13.0 产品源码上实际失败，固定代码通过。测试使用虚构凭据。

### 2. Android Auto 迟到回复会答复下一次请求（P2）

原生仅按 `parentId` 保存等待者。一次请求五秒超时后重新打开相同列表，上一轮迟到的 JS 回复会取走新等待者，还会取消新超时。服务重建也存在同类混淆。

修正：每批请求使用唯一编号，JS/adapter 原样回传。仅匹配当前编号的回复/超时才能取走等待者、移除超时；同批并发浏览仍合并，五秒期限不变。销毁服务释放全部等待者。

真实 Kotlin/JVM 四项测试通过；删除编号比较的 scratch mutant 四项中两项失败。JS 测试覆盖请求编号穿过资料库和 adapter。尚无实体车机验收。

### 3. Android 17 加固检查的日志覆盖不完整（P2，测试证据问题）

原检查只读最终 logcat 和 dumpsys audio。Maestro 2.8.0 启动日志捕获时会清空 logcat（已有 startup capture 的注释也记录了这一点）；早期记录可能不在最终快照里。因此旧绿色结果不能单独证明整轮没有 AudioHardening 事件。

修正：加固模式在模拟器 adb root 重启后、对照开始前启动独立 host 日志流，贯穿全部场景。必须真正观测到首尾标记、采集进程仍存活且未报错，才允许声明没有拦截；退出时清理进程。最终扫描合并 host 流与设备快照，原 system_server、应用进首页及替身被拦对照继续必需。

44 项本地 shell 检查通过，包括 FIFO 模拟的实际采集生命周期、旧日志被清空、采集死亡、stderr 和标记缺失。忽略 host 流的 mutant 被新“早期拦截”回归拒绝。新脚本尚需 Android 17 真实模拟器验收；不能把旧 Beta #202 当作本次完整采集的证据。

### 新的本地源码复现：pull AO 短读

使用锁定的 mpv `41f6a645068483470267271e1d09966ca3b9f413`，`native/mpv/diagnose-short-read.py` 校验整个 `audio/out/buffer.c` 的 SHA，提取并真实编译 `ao_read_data_locked()`，只替换队列/唤醒边界：

```text
requested=2400 copied=1024 expected=0.064000 reported=0.150000 excess=0.086000
requested=2400 copied=2400 expected=0.150000 reported=0.150000 excess=0.000000
```

AudioTrack 调用链先用请求长度计算 `out_time_ns`，再以 `pad_silence=false` 读取；共享函数即使短读也保存整个请求的结束时间。位置计算会减去这份过大的队列延迟。该机制能在 host 上产生86ms偏差，不依赖 JS 兜底或实际 seek 提前。

但原设备附件没有每次 AO 请求/实际读取的帧数，所以目前仍是**已复现的源码机制和设备根因候选**，不是设备根因已证实，也没有证明它解释253ms失败。没有改动 `libmpv.so`、AAR 或其已审来源清单，没有把 host 模型冒充 Android 执行。

复现：在干净的上述 mpv checkout 上运行：

```sh
python3 -I native/mpv/diagnose-short-read.py /path/to/pinned-mpv
```

下一步应在隔离诊断构建记录同代 AO 的请求/实际读取/写入帧数、时间戳与延迟，把异常时刻同第一新读数关联。确认命中后才改 native 计时、重建并核对四 ABI，再以原门限验收。不要钳制 JNI time-pos、丢第一读数、换晚窗口、放宽门限或为了碰绿重跑旧失败。引擎位置/解码代码阅读均不等于物理音频证据。
